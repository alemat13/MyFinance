# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

MyFinance — personal finance dashboard. **Python FastAPI** backend + **React 19 / Vite 6** frontend.

```
backend/   FastAPI + SQLAlchemy 2.x + SQLite (single finance.db) locally, Postgres in production via DATABASE_URL
frontend/  React 19, TypeScript 5.6, Vite 6, Tailwind CSS v4, recharts, lucide-react
```

No monorepo tool, no workspaces. No linters/formatters/type-checking configured on the Python side. No routing or state-management libs on the frontend. For local/dev, day-to-day schema changes go through `drop_all`/`create_all` via `seed.py` — fast and destructive, unrelated to Alembic below. Production (Cloud SQL Postgres, persistent real data, never reseeded on deploy) relies on two complementary mechanisms: `database.sync_schema()`, run at startup right after `create_all`, adds any model column missing from an already-existing table — **additive only** (backfills a sensible default for new NOT NULL columns, never drops/renames/retypes) — and **Alembic** (`backend/alembic/`), which handles everything `sync_schema()` can't: renames, retypes, drops, and any non-trivial backfill. `alembic upgrade head` runs automatically in CI/CD before every production deploy (see `.github/workflows/ci-cd.yml`'s `deploy` job) — see "Database migrations" below for the authoring workflow.

## Git workflow

- `main` is the production/deploy branch — pushing to it (via merged PR) triggers `.github/workflows/ci-cd.yml`'s `deploy` job, which redeploys both Cloud Run services. **`main` is branch-protected: direct pushes are rejected, merges require an open PR with passing `test-backend`/`test-frontend` checks.**
- `develop` is the default branch and where all feature work happens. Branch off `develop` for new work, open PRs back into `develop`. Pushes/PRs to `develop` run the test jobs but never deploy.
- To ship, open a PR from `develop` into `main`. Once merged, CI deploys automatically.
- Always create a feature branch off `develop` — never commit directly to `main`, and avoid committing directly to `develop` for anything non-trivial.

## Commands

### Backend
```sh
cd backend
pip install -r requirements.txt          # install deps
uvicorn main:app --reload                # dev server on :8000
python seed.py                           # drops & recreates all data
pytest                                   # run all backend tests
pytest tests/test_accounts.py            # run a single test file
pytest tests/test_accounts.py::test_name # run a single test
```

### Database migrations
```sh
cd backend
alembic revision --autogenerate -m "describe the change"  # write a new migration
alembic upgrade head                                      # apply pending migrations locally
alembic downgrade -1                                      # revert the most recent one
alembic history                                            # list all revisions
```
Write a migration **before** running `seed.py`/reseeding — with your local DB still at
the *old* schema, `--autogenerate` diffs it against the *new* `models.py` and gets the
right result. Always review the generated script: autogenerate sees a column rename as
a drop+add, so rewrite those to `op.alter_column(...)` by hand (same reasoning as the
old hand-written SQL migrations in `backend/migrations/`, now superseded — see that
directory's README). Test with `alembic upgrade head` locally before committing. CI/CD
runs `alembic upgrade head` automatically before every production deploy — no manual
`psql` step needed for a change captured as a migration.

### Frontend
```sh
cd frontend
npm install
npm run dev                     # Vite dev server on :5173
npm run build                   # tsc && vite build
npm test                        # vitest, run once
npm test -- --watch             # vitest, watch mode
npm test -- AccountsList        # run tests matching a name/file
```

### End-to-end tests
```sh
cd e2e
npm install
npx playwright install --with-deps chromium   # one-time browser install
npx playwright test                           # runs against a real backend + frontend + finance.db
npx playwright test tests/01-crud.spec.ts     # run a single spec file
npx playwright show-report                    # view the HTML report from the last run
```
A real full-stack suite (Playwright + Chromium) — no mocked API. `playwright.config.ts`'s
`webServer` entries start the real `uvicorn` backend and `vite` dev server (ports
8000/5173) and wait for both to be healthy; its `globalSetup` then runs `backend/seed.py`
once to reset `finance.db` to a deterministic state before any test file runs. Runs sequentially
(`workers: 1`) against the same SQLite file, so specs are numbered (`01-crud`,
`02-transactions-splits`, `03-import-csv`, `04-backup-restore`) to guarantee order — the
last one exercises "Overwrite all data" backup restore, which must run after everything
else. Wired into CI as the `test-e2e` job (`.github/workflows/ci-cd.yml`), gating `deploy`
alongside `test-backend`/`test-frontend`. `@playwright/test` is pinned to an exact version
in `e2e/package.json` (not a range) because Playwright requires its installed package
version and bundled browser binaries to stay in lockstep — installing a browser for a
different version than what's pinned will fetch the wrong revision. To bump it: `npm
install @playwright/test@<version> --save-exact` in `e2e/`, then `npx playwright install
--with-deps chromium` to fetch the matching browser revision, then re-run the suite before
committing the version bump.

## Architecture

- **Entities**: `User`, `Account`, `Category`, `Transaction`, `AccountUser` (junction table for account ownership), plus `CategorySplit`, `GlobalSplitWeight`, `AccountSplitWeight` (the three split-weight prefill tiers), `TransactionSplit` (a transaction's own stored weight + derived share) and `TransactionHistory` (audit trail). `Transaction.divide_group_id` (nullable, not a FK) links the transactions produced by "dividing" one transaction into several — see "Dividing a transaction" below; unrelated to `TransactionSplit`. Full ERD and column details in `docs/data-model.md`.
- **Category hierarchy**: `Category` has a self-referential, optional `parent_id`, capped at exactly 2 levels (a subcategory's parent must itself be top-level — enforced in `rules.py`, not at the DB level). A subcategory's `type` must match its parent's, and a category with existing subcategories can't have its own `type` or `parent_id` changed. Both parent and child categories remain directly assignable to a transaction; subcategories don't inherit the parent's split-weight tier or roll up into the flat `by_category` chart aggregation. The Charts page's "Spending per month" chart is a deliberate exception: it rolls a subcategory's spend up into its parent for the top-level view, and supports drilling into a parent's direct subcategories (plus a segment for transactions filed directly under the parent) — see "Charts page" below.
- **Multi-user ownership**: accounts can be jointly owned via `account_users`, which stores an `ownership_percentage` per (account, user). The backend enforces percentages sum to exactly 100% per account (422 if not, within 0.01 tolerance). This is entirely separate from split weights (below) — ownership only drives visibility filtering and the "paid" side of balances, never share amounts.
- **User-scoped filtering**: `GET /api/transactions`, `/api/accounts`, `/api/dashboard` accept `?user_id=X`, filtering to accounts where that user has `ownership_percentage > 0`.
- **Delete protection**: deleting an account/category with existing transactions returns 409; deleting a category with existing subcategories returns 409; deleting a user who still owns an account returns 409. Deleting a user who is the sole participant in some transaction's split re-resolves that transaction's split via the category > account > global cascade instead (since splits are mandatory); it only 409s if that cascade also comes up empty (no other user has a usable weight anywhere).
- **Account balances** (`backend/account_totals.py`): an account's balance is derived, never stored — `Account.balance_offset` (internal, never serialized) plus the sum of that account's transaction amounts, assembled in `serializers.build_account_out(account, transaction_total)` and reported as `AccountOut.balance`. So the dashboard/Accounts figure moves with transaction activity instead of staying frozen at whatever was typed at creation. The API still speaks only in balances: `AccountCreate.balance`/`AccountUpdate.balance` are the account's balance *right now*, and `PUT /api/accounts/{id}` stores `entered balance − current transaction total` as the offset (`offset_for_balance()`), so the account displays exactly what was entered until its next transaction. Reads go through the cached whole-table total (`get_transaction_totals()`, `account_totals` namespace); the write path uses the uncached single-account `transaction_total()`, since a stale total there would be baked into the stored offset rather than just displayed. `backup`'s `AccountExport.balance` is likewise the displayed balance, with the offset re-derived on import against the archive's own transactions.
- **Account archival**: `Account.archived` (default `false`) marks a closed account. Archived accounts are excluded from `GET /api/dashboard`'s `accounts` list and from the frontend's new-transaction account picker, and `POST /api/transactions` rejects (422) creating a new transaction against one — but `GET /api/accounts`, existing transactions, balances, and charts are unaffected, so an archived account stays visible (and un-archivable) in the Accounts list.
- **Splits & balances** (`backend/split_engine.py`): every transaction *must* store its own integer `weight` per involved user in `transaction_splits` — splits are mandatory, never optional — freely editable by the client or bulk-filled via a quick-access button from one of three tiers — `global_split_weights` (lowest priority) → `account_split_weights` (middle) → `category_splits` (highest) — resolved by `resolve_default_weights()`. If the client omits `split_weights` on create/update, the server resolves one itself via this same cascade rather than leaving the transaction unsplit; an explicit empty `split_weights` list is rejected (422) rather than clearing the split. This is only possible because `global_split_weights` is a guaranteed non-empty floor: every user gets `weight=1` there automatically on creation (`POST /api/users`), and `PUT /api/split-weights` refuses to save it empty or all-zero — unlike the account/category tiers, which may legitimately be left unconfigured. Deleting a user who's the sole participant in a transaction's split re-resolves that transaction via the same cascade (or 409s if even that comes up empty). `share_amount` is always derived from `weight` + the current `amount` via `prorate()` (2-decimal rounding, remainder to the highest `user_id`) and recomputed/persisted on every create/update; it's never itself client-editable. `GET /api/balances` (and `GET /api/dashboard`) reports each user's net position (`paid − share`) per currency, still driven by `ownership_percentage` on the "paid" side. `GET/PUT /api/split-weights` and `GET/PUT /api/accounts/{id}/split-weights` back the global and account weight-tier settings UI.
- **Dividing a transaction**: separate from Splits & balances above — that divides a transaction's amount among *users*; this (`POST /api/transactions/{id}/divide`, `routers/transactions.py`) divides *one transaction into several new transactions*, by category/date/amount, e.g. a single purchase that was really two different categories, or an amount that should be spread across two accounting months. The original transaction is updated in place to become the group's "anchor" part (keeping its `id` and `transaction_history` trail); the rest become new `Transaction` rows on the same account. Every part's `divide_group_id` is set to the anchor's own `id` (`rules.validate_divide_parts` requires the parts' amounts to sum exactly to the original amount and at least 2 parts; `rules.validate_not_divide_sibling` blocks dividing a non-anchor part directly — only the anchor can grow the group further). Each part's own `transaction_splits` is resolved independently via the normal `resolve_default_weights()` cascade unless the request supplies its own. `GET /api/transactions/{id}/divide-siblings` lists a transaction's divide-mates. History rows for both the anchor's update and each new part's creation are tagged `source="divide"`.
- **CSV import** (`backend/import_csv.py`): `POST /api/import/detect`, `/preview`, `/commit` drive column auto-detection and a preview-before-commit flow for bulk transaction upload.
- **Backup & restore** (`backend/backup.py`): `GET /api/backup/export` / `POST /api/backup/import` export/import the full database as a zipped JSON archive.
- **OneDrive automatic backup** (`backend/onedrive.py`, `routers/onedrive.py`): a single global connection (`OneDriveBackupSettings`, one row for the whole household DB, not per-user) that uploads a `backup.export_to_zip_bytes()` archive to a user-chosen OneDrive folder on a Daily/Weekly/Monthly schedule, retaining only the last `retention_count` files there. OAuth (Microsoft identity platform authorization-code flow) connects the account via `GET /api/onedrive/auth/start` → `/auth/callback`; tokens are Fernet-encrypted at rest (`ONEDRIVE_TOKEN_ENCRYPTION_KEY`) and never returned by the API. There's no restore-from-OneDrive path — restoring one of these backups still goes through the existing `POST /api/backup/import` after downloading it manually. Cloud Run has no persistent process, so the actual trigger is external: GCP Cloud Scheduler calls `POST /api/onedrive/backup/run-due` periodically (protected by a shared-secret header checked against `ONEDRIVE_SCHEDULER_SECRET`, independent of Cloud Run IAM), and the endpoint itself decides whether a backup is actually due (`onedrive.is_backup_due()`). `POST /api/onedrive/backup/run-now` triggers one immediately, for manual verification.
- **Bank sync** (`backend/enable_banking.py`, `routers/bank_sync.py`): pulls transactions straight from a bank through **Enable Banking**'s PSD2 aggregation API. Picked over GoCardless Bank Account Data (ex-Nordigen), which stopped accepting new signups in mid-2025; Enable Banking's self-serve "restricted production" mode covers exactly this case (an application that may only reach accounts its own owner has linked). Two tables: `BankConnection` (one consent per bank — several rows, unlike `OneDriveBackupSettings`) and `BankAccountLink` (one remote account, plus the `accounts.id` it feeds, `NULL` until mapped). **No token is stored**: Enable Banking authenticates the app with an RS256 JWT signed per request from `ENABLE_BANKING_PRIVATE_KEY` (`kid` = `ENABLE_BANKING_APPLICATION_ID`), so there's no OAuth exchange and no Fernet column like OneDrive's. Flow: `POST /api/bank-sync/connections` → `enable_banking.start_authorization()` → the browser is redirected to the bank → the bank returns it to `GET /api/bank-sync/callback` → `POST /sessions` records the accounts the consent covers. A session names its accounts in either of two shapes — whole account objects in `accounts`, or bare uid strings there and/or in `accounts_data` — so `_session_accounts()` reads and merges both, and falls back to `GET /accounts/{uid}/details` for the IBAN/name/currency when only a uid came back (CCF returns objects, BoursoBank returned an empty `accounts`). A consent that names no account is still recorded as `linked`, with `last_error` naming what the session actually contained; `POST /api/bank-sync/connections/{id}/refresh` re-reads it via `GET /sessions/{id}`, which repairs such a connection without a new authorization and preserves existing account mappings. **Nothing inbound is ever needed** — Enable Banking has no webhook for account data, only the user's own browser comes back, which is what makes this work behind IAP unchanged. Deduplication is `transactions.external_id` (the bank's `entry_reference`/`transaction_id`, or a derived `fp:` fingerprint) under a unique index on `(account_id, external_id)`, plus a one-shot date+amount guard against pre-existing rows that carry no `external_id` at all — that's what stops a sync re-importing the migrated ledger. Imports go through the same `resolve_default_weights()` cascade, audit rows (`source="bank_sync"`) and cache invalidation as CSV import; synced transactions arrive uncategorized. Scheduling mirrors OneDrive exactly and for the same reason (no long-lived Cloud Run process, and a mass import once held a Postgres transaction open long enough to take production down): GCP Cloud Scheduler calls `POST /api/bank-sync/run-due` with `X-Bank-Sync-Scheduler-Secret`, the endpoint decides what's actually due (`is_sync_due()`, floored at 6h since banks cap account endpoints at 4 calls/day), and each link commits on its own. `POST /api/bank-sync/links/{id}/sync` runs one immediately.
- **Raw, read-only transaction fields**: `transactions.raw_source`, `raw_label`, `raw_counterparty`, `raw_transaction_code`, `raw_merchant_category_code`, `raw_merchant_location`, `raw_initiated_date` (Alembic `0014`) hold what the source reported before anyone renamed anything. They are absent from `TransactionCreate`/`TransactionUpdate` on purpose — present only on `TransactionOut` — and take part in no computation whatsoever (no balance, no chart, no split, no cache namespace), so nothing invalidates when they change. `payee`/`memo` are the user's to rewrite; these are the frozen copy, which is what makes categorisation and rename suggestions trainable on real history rather than on already-cleaned labels. **Two feeds write the same columns**: `enable_banking.normalize_transactions()` for newly synced rows, and a backfill from the Linxo GDPR export for the migrated history. `raw_source` is what says which, because the vocabularies differ — `raw_transaction_code` is an ISO 20022 domain/family/sub-family from a bank and a Linxo transaction type (`PointOfSale`, `DirectDebit`) from the export, and nothing tells them apart from the value alone. They round-trip through `backup.py` (`TransactionExport`), since a restore that dropped them would silently undo a backfill nothing else can redo — the Linxo export is a one-off file, not a feed. Surfaced by `frontend/src/components/TransactionRawFields.tsx`, a collapsed read-only section in `TransactionDetail` that renders nothing when every field is empty.
- **Audit trail** (`backend/audit.py`): every transaction create/update/delete writes a snapshot row to `transaction_history`, readable via `GET /api/transactions/{id}/history`. Its FK-like columns (`transaction_id`, `changed_by_user_id`) are deliberately plain integers, not real foreign keys — see the comment in `models.py`.
- **Charts page** (`backend/charts.py`, `routers/charts.py`): `GET /api/charts` takes `user_id` (required), plus optional `currency`, `start_month`/`end_month` (`"YYYY-MM"`, filtered against each transaction's *computed* accounting month, not its raw `date`), and `parent_category_id`. Two charts are built from the same response: **Net income per month** (`by_month`/`net_by_month`, unchanged from the original per-category/per-month aggregation) and **Spending per month** (`by_month_category`/`chart_categories`/`parent_category`, Expense + Uncategorized only). With no `parent_category_id`, `by_month_category` rolls a subcategory's spend up into its parent (`category.parent_id or category.id`); with one, it's scoped to that category's own subtree — rows categorized directly on the parent itself *and* rows on each direct child both appear as their own segment, since MyFinance (unlike the Linxo view this chart is modeled on) allows both. `parent_category_id` must be a top-level Expense category or the endpoint 400s.
- **Backend layout**: `main.py` (FastAPI app, lifespan, CORS, exception handlers, router registration only — no route bodies), `routers/` (one `APIRouter` per resource: `users.py`, `accounts.py`, `categories.py`, `transactions.py`, `split_weights.py`, `balances.py`, `imports.py`, `backup.py`, `onedrive.py`, `bank_sync.py`, `dashboard.py`, `charts.py`), `serializers.py` (ORM object → Pydantic response-model builders, e.g. `build_account_out`, `get_transaction_out`), `rules.py` (cross-field/DB-dependent input validation, e.g. `validate_weights`, `validate_category_hierarchy`; raises `RuleViolation`, mapped to 422 by a dedicated handler in `main.py`), `models.py` (SQLAlchemy ORM), `schemas.py` (Pydantic I/O schemas), `database.py` (engine/session, `sync_schema()`), `seed.py` (destructive seeder), `alembic/` (migration environment + `versions/`, see "Database migrations" above), plus `accounting_month.py`, `audit.py`, `backup.py` (business logic; distinct from `routers/backup.py`), `onedrive.py` (business logic; distinct from `routers/onedrive.py`), `enable_banking.py` (business logic; distinct from `routers/bank_sync.py`), `cache_service.py` (aggregate-result caching, see below), `charts.py` (business logic; distinct from `routers/charts.py`), `filtering.py`, `import_csv.py`, `split_engine.py`.
- **Aggregate caching** (`backend/cache_service.py`): `GET /api/dashboard`, `GET /api/balances`, and `GET /api/charts` all derive from Python-side aggregation over every relevant `TransactionSplit` row (`split_engine.compute_balances()`, `charts.compute_chart_data()`) rather than a SQL `SUM`/`GROUP BY` — expensive to redo on every load. The `account_totals` namespace caches a cheaper aggregation (one `SUM`/`GROUP BY` over `transactions`) for the same reason: `GET /api/dashboard` and `GET /api/accounts` need it on every load, over tens of thousands of production rows. `cache_service.get_or_compute(db, namespace, params, compute)` caches a JSON-serializable result in the `aggregate_cache` table, keyed by a namespace (`balances`, `charts`, `account_totals`) plus params (e.g. `user_id`, `currency`); `cache_service.invalidate(db, *namespaces)` drops every entry in the given namespace(s) and is called at every mutation site that could change those sums (transaction create/update/delete/bulk-update/bulk-delete/divide, CSV import commit, an account's currency/ownership update, a category's type update, deleting a user whose split re-resolution can change other users' shares) — always right before that mutation's own `db.commit()`, so the invalidation lands atomically with the change. `cache_service.invalidate_all(db)` drops the entire cache and is used only by bulk backup restore (`backup.import_database`), which bypasses every other mutation path. It's a plain DB table rather than an in-process cache (`functools.lru_cache`/module dict) because the backend can run multiple Cloud Run instances (`--max-instances=2`) — an in-process cache would go stale on instances a write didn't land on. A new aggregation (e.g. a future per-account/per-month breakdown) just needs its own namespace, a `get_or_compute` call, and `invalidate()` calls at whatever mutation sites can affect it — `cache_service.py` itself is generic and needs no changes.
- **Frontend entrypoint chain**: `index.html → main.tsx → App.tsx → Dashboard.tsx`. `App.tsx` owns view-switching (no router, plain `useState`) across 11 views — `dashboard`, `accounts`, `categories`, `transactions`, `users`, `split-settings`, `import`, `bank-sync`, `backup`, `charts`, `help` (`View`/`viewLabels`/`viewIcons`/`PRIMARY_VIEWS`/`MORE_VIEWS` in `nav.ts`) — and the user-selector dropdown (persisted to `localStorage`, filters all views via `user_id`), plus a `FirstLaunchUserPrompt` overlay shown before a user is chosen. Navigation itself is `NavShell.tsx`: one nav bar (Dashboard/Transactions/Accounts/Charts always visible, plus a "More" button opening a `Sheet` for the rest) that's repositioned by breakpoint alone — a fixed bottom tab bar below `md`, an inline bar under the header at `md` and up — rather than rendered twice, so there's one set of nav buttons in the DOM at any width (see `hooks/useMediaQuery.ts` below). Cross-view deep links go through the query string rather than props: `navigateToAccountTransactions()` (wired to `Dashboard`'s account tiles via `onSelectAccount`) writes `view=transactions&account_id=X` and clears every other simple/advanced transaction filter before switching the view, since `TransactionsPage` reads its filters from the URL on mount.
- **Frontend list views** (`AccountsList`, `CategoriesList`, `TransactionsPage`, `UsersList`) do full CRUD with inline New/Edit/Delete forms — no modals, except `TransactionsPage`: both creating a transaction (via "+ New Transaction") and clicking an existing row open `TransactionDetail`, a single `Modal`-based create/view/edit/delete/history panel (`transactionId: number | null`, `null` meaning create mode; editing an existing transaction is bookmarkable via a `?transaction=` URL param, creating one is not). The Delete button and History section only render once the transaction exists (`transactionId !== null`). The account form includes two independent multi-row sub-tables: per-user ownership percentages, and the account's own split-weight tier. `CategoriesList` edits the category weight tier the same way, plus a "Parent category" selector (locked once a category has its own subcategories); its table groups subcategories under their top-level parent with an expand/collapse chevron, a subcategory count, and an inline "+ Add subcategory" action pre-filling the parent and locking the type. `TransactionDetail` uses `TransactionSplitFields` — an always-visible integer-weight editor with "Global"/"Account"/"Category" tier quick-fill buttons, a "Split Evenly" button, a quick-fill button per user (assigns that user alone), and a live-computed (client-side `prorateWeights()`, mirroring the backend) read-only euro amount per row. Category selection everywhere on the Transactions screen (`TransactionDetail`'s form, and both the simple and advanced filters) uses the shared `CategoryPicker` — a searchable popover grouping subcategories under their parent, with the parent itself also selectable — instead of a plain `<select>`. `TransactionDetail` also has a "Divide" button (existing transactions only, hidden for a non-anchor divide part) opening `TransactionDivideModal` — an add/remove-able list of parts (date, accounting-month offset, payee, memo, amount, category), gated on a live "remaining to allocate" total reaching zero; on success it closes both modals and refreshes the list. A transaction that's part of a divide group shows a "Divided transaction" section linking to its sibling parts (`onNavigateToTransaction`, wired from `TransactionsPage`'s `openDetail`). An **Export CSV** button next to "+ New Transaction" downloads every transaction matching the current filter (simple or advanced) across all pages — not just the page shown — via `POST /api/transactions/search` with `unpaginated: true` (skips the endpoint's normal `page`/`page_size`/200-row-cap pagination while still applying every filter/sort); the CSV includes every transaction field plus a Weight/Share/Balance column per household user (pivoted, via `utils/csv.ts`'s `buildCsv()`). Other views: `SplitWeightsSettings` (global weight tier settings) + `SplitEditor` (the generic row-editor reused by all four weight/percentage tables), `BalanceWidget` (net-position display), `ChartsPage` (a shared From/To month-range filter and currency selector feeding `charts/SpendingByMonthChart` — a stacked, click-to-drill-into-subcategories recharts `ComposedChart` — and `charts/NetIncomeByMonthChart`, replacing the page's earlier three separate charts), `CsvImportPage`, `BankSyncPage` (connect a bank, map each remote account to a MyFinance one, sync now, and disconnect — the bank list loads separately from the rest so a missing/failing Enable Banking config doesn't hide the already-connected banks), `BackupPage` (also renders `OneDriveBackupCard`, the connect/settings/disconnect UI for the OneDrive automatic backup feature above).
- **Shared frontend infra**: `components/ui/` holds the design-system primitives — `Button`, `Badge`, `Card`, `Input`/`Select`, `Table` are plain Tailwind (via `cva()` variants and the `cn()` helper in `lib/utils.ts`, which merges classes with `tailwind-merge`); `Modal` and `Sheet` wrap `@radix-ui/react-dialog` (a11y focus trap/nested-Escape-stacking/background inerting come from Radix, not hand-rolled). `Modal`'s `size="lg"` goes edge-to-edge below `md` (a full-page sheet on mobile) and becomes a centered, width-capped dialog at `md` and up; `size="sm"` (confirm dialogs) always stays a centered card. `hooks/useMediaQuery.ts`'s `useIsMobile()` (matches `(max-width: 767px)`) is for cases where a *different* markup tree must render on mobile (e.g. `TransactionsPage` and `TransactionList`'s card-list-vs-table), as opposed to the pure-CSS `md:` breakpoint switching `NavShell` and `Modal` use — picking one render path in JS avoids ever mounting two copies of the same interactive content (checkboxes, row text) at once, which would otherwise break `getByText`/`getByRole` queries in tests since jsdom doesn't evaluate media queries. `setupTests.ts` stubs `window.matchMedia` to always report no match, so existing tests stay on the desktop path unless a test overrides it. `context/` holds `ThemeContext` (dark mode) and `ToastContext`, `utils/` holds `currency.ts`, `download.ts`, `csv.ts` (RFC 4180 `escapeCsvField()`/`buildCsv()`, used by the Transactions CSV export), `splitWeights.ts` (client-side `prorateWeights()`/`resolveDefaultSplitRows()`, mirroring `split_engine.py`), `categoryHierarchy.ts` (client-side mirror of the backend's 2-level category grouping/parent-validation rules, used by `CategoriesList` and `CategoryPicker`), `transactions.ts`, `urlState.ts`, `dateRange.ts` (`lastNMonthsRange()`/`monthsBetween()`, mirroring `accounting_month.py`'s month arithmetic, used by `ChartsPage`). Styling is Tailwind CSS v4 utility classes (`index.css`), not a hand-rolled stylesheet.
- **PWA installability** (`frontend/vite.config.ts`'s `VitePWA()`, `frontend/public/icons/`): the app is installable to a phone's home screen (manifest + a service worker generated by `vite-plugin-pwa`, `registerType: 'autoUpdate'`) so it opens without browser chrome. The service worker precaches the **app shell only** (`workbox.globPatterns` covers the built HTML/JS/CSS/icons) — that's what makes Chrome's install path accept the app, since it wants `start_url` answered with a 200 while offline. Navigations are **network-first**, not cache-first: production sits behind Google IAP, which re-authenticates an expired session by redirecting a navigation to Google's sign-in page, and answering navigations from the cache would swallow that redirect and leave the app stuck on a shell whose every API call fails. That's why `navigateFallback` is left unset in favour of a `NetworkFirst` runtime-caching route whose `handlerDidError` falls back to the precached `index.html`, and why `directoryIndex: null` is set — otherwise workbox's own precache route answers `/` from the cached `index.html` before that strategy ever runs. It is not an offline data story: every figure on screen still comes from the API, so launching offline gets you the app with nothing in it. Leaving `globPatterns` empty is what originally broke installability, and it also made `sw.js` throw `non-precached-url` on startup, since the generated `createHandlerBoundToURL('index.html')` needs `index.html` to actually be in the precache. `index.html` carries the matching `apple-touch-icon`/`apple-mobile-web-app-*` meta tags Safari needs (it doesn't read the web manifest for these), plus `viewport-fit=cover` and the `pt-safe`/`pb-safe`/`pb-bottom-nav` utility classes (`index.css`) for notch/home-indicator safe-area insets.
- **API client**: `frontend/src/api/client.ts`, fetch-based. Base URL is `` `http://${window.location.hostname}:8000/api` `` unless overridden by the `VITE_API_URL` build-time env var — not hardcoded to `localhost`.

## Documentation

- User-facing behavior changes (new/changed views, forms, buttons, flows) **must** be reflected in `docs/user-guide.md` in the same PR — don't leave it stale. Schema/entity changes likewise require updating `docs/data-model.md`. When editing `models.py`, `main.py` routes, or `frontend/src/` in ways that change what a user sees or does, check whether `docs/user-guide.md` needs a matching update before considering the task done, and do the same for this file (`CLAUDE.md`) when architecture, commands, or workflow change.

## Key gotchas

- `seed.py` **destroys existing data** — `drop_all` then re-inserts sample rows. Never run it against production.
- Adding a new nullable-with-scalar-default column to a model is safe to deploy straight to production — `sync_schema()` backfills it automatically on next startup, no migration needed. Anything else (rename, retype, drop, a NOT NULL column with no usable default) needs an Alembic migration (`alembic revision --autogenerate`, reviewed and tested locally) committed alongside the model change — CI/CD applies it automatically before deploy, so a merged PR with the migration file just works.
- CORS origins default to `http://localhost:5173` plus a couple of LAN/Tailscale dev origins (`backend/main.py`), but are fully overridable via the `CORS_ALLOWED_ORIGINS` env var (comma-separated) — production sets this explicitly in `ci-cd.yml`.
- No `.env` is actually used, though `.env` is gitignored — runtime env vars (`DATABASE_URL`, `CORS_ALLOWED_ORIGINS`, `VITE_API_URL`) are instead set via Docker build args / Cloud Run env vars in CI.
- OneDrive automatic backup needs six env vars the app doesn't set defaults for meaningfully in production: `ONEDRIVE_CLIENT_ID`/`ONEDRIVE_CLIENT_SECRET`/`ONEDRIVE_REDIRECT_URI` (from a one-time, manual Azure AD app registration granting `Files.ReadWrite offline_access`), `ONEDRIVE_TOKEN_ENCRYPTION_KEY` (a `cryptography.fernet.Fernet.generate_key()` value — generate once and never rotate without also re-encrypting any already-stored tokens, or reconnecting), `ONEDRIVE_SCHEDULER_SECRET` (shared secret the Cloud Scheduler job sends as `X-Backup-Scheduler-Secret`), and `FRONTEND_BASE_URL` (where `/auth/callback` redirects back to after connecting). The Cloud Scheduler job itself is also a one-time manual `gcloud scheduler jobs create http` setup, not something CI/CD provisions.
- Bank sync needs four env vars with no useful defaults in production: `ENABLE_BANKING_APPLICATION_ID` and `ENABLE_BANKING_PRIVATE_KEY` (from a one-time, manual application registration in Enable Banking's Control Panel — the private key is the RSA key whose public half was uploaded there, and it is the *entire* credential, so it lives in Secret Manager and never in the repo; a literal `\n`-escaped PEM is handled), `ENABLE_BANKING_REDIRECT_URL` (must match a redirect URL registered on that application, and points at `/api/bank-sync/callback`), and `BANK_SYNC_SCHEDULER_SECRET` (shared secret the Cloud Scheduler job sends as `X-Bank-Sync-Scheduler-Secret`). Like OneDrive's, the Cloud Scheduler job itself is a one-time manual `gcloud scheduler jobs create http` setup, not something CI/CD provisions.
- Backend tests use `sqlite:///:memory:` with `dependency_overrides[get_db]`; tables are created/dropped per test session (see `backend/tests/conftest.py`).
- Frontend component tests mock `src/api/client` via `vi.mock`; API-client tests mock `global.fetch` directly instead.
- Components using `alert()`/`confirm()` need those mocked with `vi.spyOn` in their tests.
